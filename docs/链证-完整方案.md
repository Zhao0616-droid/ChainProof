# （一）产品概述与定位

## 1. 背景与目标

### 行业背景

智能合约漏洞造成的损失以百亿美元计，而现有审计手段两头都有缺口：

| 手段 | 缺口 |
|---|---|
| **人工审计** | 昂贵（一次数万至数十万美元）、周期长（数周）、产能有限 |
| **自动化检测工具**（Slither / Mythril / Oyente 等） | 快，但**误报率高**——审计师要花大量时间筛假问题 |
| **形式化验证工具**（Certora / VeriSolid 等） | 结论**可证明**，但需要**领域专家手写形式化规约**，门槛极高、落不了地 |

### 核心痛点

> **形式化验证几十年落不了地，瓶颈从来不是求解器，是"谁来写规约"。**

写 invariant / specification 需要专家一笔一划推导，这是它无法规模化的根本原因。

### 产品目标

**把"专家写规约"变成"AI 自动生成 + 求解器机器证明"。** 让可证明的安全结论，从少数专家手里释放到每一个开发者手里。

### 对人工智能软件领域发展的意义

本作品验证了一条**可复用的软件架构范式**：

> **AI 负责生成，确定性内核负责裁决。**

这套"**AI 生成 + 形式化验证 + 反馈闭环**"的结构不只适用于智能合约，它可以迁移到任何"**有明确规范、但判定昂贵**"的场景——合同条款审查、工业工艺合规、数据一致性核验、协议栈安全验证。本作品的价值不只在于一个审计工具，更在于为"**可信 AI 软件**"提供了一个可复制的工程范式：**AI 的能力边界由架构划清，而不是由提示词祈祷。**

## 2. 产品定位

| 项 | 内容 |
|---|---|
| 产品类型 | AI 辅助分析工具 · 在线服务（Web + CLI + CI） |
| 目标用户 | 高校区块链课程与竞赛团队 · 联盟链/产业区块链开发者 · 独立开发者 |
| 核心场景 | 合约开发过程中的持续安全审计 · 教学中的漏洞原理学习 · 提交前的安全自查 |

### 三个维度的差异化优势

| 维度 | 优势 | 量化 |
|---|---|---|
| **算法精度** | 形式化证明替代启发式猜测，误报率显著低于纯规则工具 | 检出率 / 漏报率 / 误报率三项对比 Slither·Mythril |
| **运行效率** | 沙箱并行 + 路径裁剪，批量审计可控 | 单合约分析耗时、100 合约批量耗时 |
| **场景适配性** | 支持多版本 solc（0.4-0.8）；CLI/CI 可直接接入开发流程 | 版本覆盖率、CI 接入成本 |

# （二）技术架构与创新

## 1. 整体架构

```
┌──────────────────── 产品层 ────────────────────┐
│  Web 前端（M1-M6）  │  后端 API + 任务队列      │
│  CLI  │  CI/CD 集成  │  报告导出  │  用户与权限  │
└───────────────────────┬───────────────────────┘
                        │ schemas/analysis_result.json
┌───────────────────────┴───────────────────────┐
│  AI 层                     │  引擎层            │
│  · 代码语义理解            │  · 编译（多版本 solc）│
│  · 规约生成 + 反馈闭环 ⭐   │  · 符号执行          │
│  · 路径优先级排序          │  · 反例解析          │
│  · 反例解释 / 补丁生成     │  · 漏洞模式库        │
│                           │  · 路径裁剪          │
└───────────────────────────┴───────────────────┘
                        │
┌───────────────────────┴───────────────────────┐
│  基础设施层                                     │
│  沙箱执行（容器隔离/资源限额/禁网）              │
│  可观测性（日志/指标/追踪）  ·  配置管理         │
│  存储  ·  队列  ·  部署（Docker + 反向代理）     │
└───────────────────────────────────────────────┘
```

**数据流**：

```
上传合约 → 沙箱编译 → 语义理解(AI) → 规约生成(AI) ★
        → 符号执行 → 求解器验证(Z3) → 反例解析
        → 反馈回规约生成（迭代）
        → 解释+补丁(AI) → 报告 → 应用补丁 → 重跑确认
```

## 2. 技术选型

### AI 技术选型

| 位置 | 选定 | 候选对比 | 选型依据 |
|---|---|---|---|
| 代码语义理解 | 长上下文代码大模型 | 通用 LLM / 静态分析 | 需要跨函数、跨合约理解；静态分析无语义 |
| **规约生成** | 代码大模型 + 求解器反馈闭环 | 人工写规约 / 纯提示工程 | 闭环让生成结果**必须通过验证** |
| 路径优先级 | 轻量分类器 / 交叉编码器 | 均匀采样 / 随机 | 路径爆炸时优先探索高价值路径 |
| 反例解释 / 补丁 | 代码大模型（漏洞类型条件约束） | 模板生成 | 需要结合具体上下文 |

### 支撑技术选型

| 类别 | 选定 | 依据 |
|---|---|---|
| 编译器 | **solc 多版本（py-solc-x / solc-select）** | 真实合约跨 0.4-0.8，单版本覆盖率不足三成 |
| 符号执行 | Mythril（主）/ Manticore（备） | 成熟、可脚本化、支持路径导出 |
| 静态分析 | Slither | 快速初筛 + 与我们的结果做对比基线 |
| 形式化验证 | **Z3（主）/ CVC5（备）** | SMT-LIB 标准、生态成熟、可复现 |
| 沙箱 | Docker 容器 + cgroup 限额 + 无网络 | **执行陌生人代码的安全底线** |
| 后端 | Python（FastAPI）+ 任务队列 | 与引擎/AI 同语言，减少跨语言成本 |
| 前端 | 现代 Web 框架 + 代码高亮组件 | 源码定位与证明展示是核心交互 |
| 部署 | Docker Compose + 反向代理 | 一键起，便于评审验证 |

## 3. 创新应用（对比同类产品）

### 核心主张

> **用 LLM 自动生成形式化规约，交给求解器证明——把形式化验证从"专家手写规约"变成"自动生成 + 机器证明"。**

### 同类产品对比

| 产品/工具 | 检测方式 | 结论性质 | 误报 | 规约来源 | 可解释性 |
|---|---|---|---|---|---|
| Slither | 静态模式匹配 | 启发式告警 | 高 | 无 | 中 |
| Mythril | 符号执行 | 路径可达性 | 中 | 无（内置检查） | 中 |
| Certora | 形式化验证 | **可证明** | 低 | **专家手写** | 高 |
| **本作品** | LLM 生成规约 + 形式化验证 | **可证明** | 低 | **AI 自动生成** | **证明可展开** |

**差异总结**：**我们的规约不是人写的，而结论依然是可证明的。**

### 诚实定位

"反例引导的精化""LLM + 求解器"这类组合**已有先例**（CEGIS 2006、Houdini 2001、PropertyGPT 等）。本作品的贡献是**应用 + 闭环 + 信号设计**，不是方法首创。按评分表语言，属于"**在现有技术上有显著改进，形成独特解决方案**"。

# （三）功能设计与实现

## 1. 核心功能

| # | 功能 | AI 实现方式 |
|---|---|---|
| F1 | **合约编译**（多版本 solc） | 非 AI：编译器封装 |
| F2 | **规约自动生成** ⭐ | 代码大模型 + 求解器反馈闭环 |
| F3 | **形式化验证** | 非 AI：Z3/CVC5 求解 SMT-LIB |
| F4 | **漏洞定位与证明展开** | 非 AI：反例解析 + 溯源 |
| F5 | **反例自然语言解释** | 代码大模型（以结构化反例为条件） |
| F6 | **修复补丁生成与验证** | 代码大模型生成 + 重跑验证 |
| F7 | **覆盖率声明** | 非 AI：已证明/未证明统计 |

## 2. 六个功能模块

| # | 模块 | 内容 | 展开维度 |
|---|---|---|---|
| **M1** | 项目空间与审计历史 | 多合约项目、多次审计、**审计 diff**（修好哪些/新引入哪些） | 时间 + 数量 + 协作 |
| **M2** | **审计结果与证明视图** ⭐ | 源码高亮 + 证明展开 + 反例轨迹 + 补丁 diff + 一键应用重跑 | 核心交互 |
| **M3** | 规约库 | 每条规约可查看/编辑/停用，标 SWC 分类与出处 | 维护 |
| **M4** | 报告导出与分享 | 行业格式报告，每个结论带证明链接 | 传递 |
| **M5** | 批量审计 + CLI + CI/CD | 批量任务、命令行、GitHub Action、PR 评论 | 数量 + 工程化 |
| **M6** | 漏洞知识库 | 按 SWC 分类：原理 + 真实案例 + 复现 + 修复 | 场景 |

## 3. 辅助功能与 AI 的协同关系

| 辅助功能 | 与 AI 的协同 |
|---|---|
| **用户与权限** | 保留每次分析的模型版本与规约版本 → **可追溯"这条结论是哪个模型版本给出的"** |
| **数据统计看板** | 漏洞类型分布 → **哪类漏洞的规约生成成功率低** → 回流补充规约样本、优化生成策略 |
| **任务队列与进度** | 暴露 AI 生成轮次、求解器耗时、超时原因 → 用于模型与策略调优 |
| **审计历史（M1）** | 历次结果的差异 → **衡量模型迭代是否真的让检出率上升** |

> 辅助功能不是 CRUD，而是**模型运维闭环的观测面**。

## 4. 扩展性设计

| 扩展点 | 设计 |
|---|---|
| **模型升级接口** | AI 层与引擎层通过 JSON 契约解耦 → 换模型只需替换 `ai/` 实现，不动引擎与前端 |
| 规约库热插拔 | 规约以数据形式存储（非硬编码），新增漏洞类型只需新增规约条目 |
| **多工具融合路径** | 符号执行引擎可替换（Mythril → Manticore → 自研）；求解器可替换（Z3 → CVC5）；已定义统一适配接口 |
| **多语言扩展路径** | 引擎的"编译-符号执行-求解"三段式与语言无关，扩展 Vyper/Rust 合约只需新增编译器适配 |
| 部署形态扩展 | CLI / Web / CI 三种消费形态共用同一引擎，可继续扩展为 IDE 插件、SaaS API |

## 1. 开发流程

- **四周冲刺 + 每日站会 + 每周集成**

- 团队分工与集成细节见《链证-分工与集成手册》

## 2. 代码实现

关键 AI 功能代码将展示：

| 展示点 | 体现的规范性 / 优化策略 |
|---|---|
| 规约生成闭环 | 生成 → 验证 → 反馈 → 重生成的迭代控制与收敛判定 |
| 求解器反馈结构化 | 把 SMT model 转成 LLM 可理解的反例描述（而非原始输出） |
| 提示词工程 | 漏洞类型条件约束 + 少样本 + 输出格式强约束 |
| 结果缓存 | 相同合约 hash 复用历史结果，降低重复算力 |
| 沙箱封装 | 资源限额、超时中断、结果回收 |

## 3. 测试优化（AI 功能专项测试方案）

### 3.1 四组专项实验

| # | 实验 | 目的 | 对照 |
|---|---|---|---|
| **E1** | **AI 必要性消融** | 证明 AI 在关键路径 | 纯规则/纯工具 vs 加规约生成 |
| **E2** | **微调 vs API** | 证明模型选型合理 | QLoRA 微调模型 vs API baseline |
| **E3** | **同类工具对比** | 证明差异化优势 | 本作品 vs Slither vs Mythril |
| **E4** | **补丁有效性** | 证明修复闭环成立 | 打补丁前后重跑 |

### 3.2 指标与真值来源

| 指标 | 测法 | 真值来源 |
|---|---|---|
| 检出率 / 漏报率 | SolidiFI 注入漏洞抓到多少 | ✅ 注入即知真值 |
| **误报率** | 干净合约跑一遍 | ✅ 未注入原版 / SmartBugs 干净合约 |
| 规约有效率 | 生成的规约抓住多少已知漏洞 | ✅ 求解器自动判定 |
| 形式化覆盖率 | 已证明性质 / 总性质 | ✅ 自动 |
| 补丁有效率 | 打补丁后漏洞是否消失 | ✅ 自动 |
| 分析耗时 | 单合约 / 批量 | ✅ 自动 |

### 3.3 按测试结果的改进措施（改进闭环）

示例改进叙事（方案中需写入真实数据）：

| 轮次 | 发现的问题 | 改进 | 复测结果 |
|---|---|---|---|
| R1 | 规约过弱，漏报率高 | 引入"反例反馈重生成" | 漏报率 A% → B% |
| R2 | 规约过强，误报升高 | 加入无关路径负样本约束 | 误报率 C% → D% |
| R3 | 复杂合约超时 | 路径裁剪 + 超时降级为部分结果 | 超时率 E% → F%，覆盖率保持 |

# （五）应用价值与展望

## 1. 应用场景

| 场景 | 使用方式 | 量化价值 |
|---|---|---|
| **高校区块链课程** | 学生提交作业合约 → 系统给出漏洞 + **可展开证明** + 修复建议；教师端看班级漏洞分布 | 作业批改与安全教学一体化；漏洞原理可视化 |
| **竞赛/训练营** | CTF 式练习：给漏洞合约，看能否被检出、能否修复 | 训练效率提升 |
| **联盟链/产业区块链开发** | 接入 CI，提交代码自动审计，PR 内评论 | 审计前置，减少人工审计轮次 |
| **提交前安全自查** | 独立开发者上传合约，拿到带证明的自查报告 | 降低上线前风险 |

**操作流程（以课程场景为例）**：
1. 学生登录 → 上传 `.sol` 文件（或粘贴代码）
2. 系统编译 → 生成规约 → 符号执行 → 求解器验证
3. 出报告：漏洞清单（按严重度）+ 每条可展开的**证明**与**反例轨迹**
4. 学生点"应用补丁" → 系统重跑 → 确认漏洞消失
5. 导出报告，附在作业里

## 2. 市场分析

| 项 | 内容 |
|---|---|
| 行业趋势 | 智能合约安全事件持续高发；国内区块链产业以**联盟链/产业区块链**为主（供应链金融、存证、政务） |

| 竞争力 | **算法**：可证明结论优于启发式告警；**功能**：审计+知识库+CI 一体；**体验**：证明可展开、结论可溯源 |

## 3. 成果总结

- **技术创新**：把形式化验证的规约生成自动化，形成"生成-验证-反馈"闭环
- **工程成果**：完整产品（Web + CLI + CI + 知识库 + 报告），支持多版本 solc，具备沙箱安全隔离
- **实验成果**：可复现的评测体系（注入漏洞真值 + 干净合约负样本），量化对比同类工具
- **范式价值**：验证"AI 生成 + 确定性裁决"的可信 AI 软件架构

## 4. 未来规划

### 当前不足（四维分析）

| 维度 | 现状 | 不足 | 改进方向 |
|---|---|---|---|
| **算法精度** | 覆盖 7 类常见漏洞 | 对复杂经济模型漏洞、跨合约不变式识别能力弱 | 引入跨合约不变式推理、结合历史攻击案例做检索增强 |
| **软件兼容性** | 支持 Solidity 0.4-0.8 主流版本 | 不支持 Vyper/Rust 合约；不支持非 EVM 链 | 抽出语言无关的"编译-执行-求解"适配层 |
| **并发处理能力** | 容器级并行，受单机资源限制 | 大规模批量（千级合约）时队列积压 | 引入分布式任务队列与弹性扩缩容 |
| **场景覆盖范围** | 面向单合约静态审计 | 缺少运行时/动态分析；缺少与测试网联调 | 接入动态模糊测试与链上运行数据 |

### 具体规划

| 阶段 | 目标 |
|---|---|
| 近期 | 扩展规约库覆盖至 15 类漏洞；引入跨合约不变式 |
| 中期 | 多语言支持（Vyper）；分布式任务队列；IDE 插件 |
| 长期 | 与形式化验证服务商/联盟链平台对接，形成"开发-审计-上链"闭环 |
